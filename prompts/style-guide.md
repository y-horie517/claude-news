# スタイルガイド

このファイルは記事の「品質の定義」です。エージェントは執筆前に必ず全文を読むこと。

## 読者プロフィール

- 日本語話者。Claude Code を日常的に使って開発している（主に Web / Next.js）。
- 関心の重点は **(A) Claude Code での開発** と **(B) チーム・業務への展開**。この2つに寄せる。
- Claude API / SDK / claude.ai チャットの話題は「開発や業務展開に効くとき」だけ取り上げる。
- Claude Daily は1日1号。10〜12分で読み切れる分量（地の文で 4,500字以内）。

## 文体

- **ですます調**。断定できることは断定し、曖昧なことは曖昧だと書く。
- 煽らない。「革命的」「爆速」などの誇張表現は使わない。
- **なぜそうするのかを必ず添える。ただし1段落3文以内で。** 理由が3文を超えるなら、それは表か図にすべき情報です。
- コマンド・設定・プロンプト例は**そのままコピペして試せる**形で書く。断片ではなく完全な形にする。

## 読みやすさの規約

読者は通勤中にスマホで読みます。**頭から順に読まないと分からない原稿は失敗**です。
ここに書いた数字は `scripts/readability-check.py` が機械的に検査します。閾値を変えるときは両方を直すこと。

### 文と段落

- 1文は **60字目安、80字を超えたら分割**。1文1主張。読点で複数の主張を繋がない。
- 1段落は **3文以内**。字数は150字目安で、**200字を超えたら必ず割る**。
- **段落の1文目に結論**を置く。理由・条件・例外は2文目以降に回す。
- **地の文が3段落、または400字を超えて続いたら、表・箇条書き・図・コードのどれかに割る。**
- 用語の定義を本文の括弧に入れない。長い修飾の入れ子になります。初出時に独立した短い文にするか、節末の用語ミニ表に出す。
  - ❌ `サブエージェント（親とは別のコンテキストで動く子セッション）を使うと…`
  - ✅ `サブエージェントを使うと…` ＋ 別行で `サブエージェント: 親とは別のコンテキストで動く子セッション`
- **太字は1段落1箇所・1節5箇所まで。** それ以上打つと、強調が強調として読まれなくなります。
  - 段落の頭に置くラベル（`**前提**: …` `**手順**` など）は見出しの代わりなので、この数に入れません。
- 数値が3つ以上絡む話は、地の文でなく**表か数値タイル**にする。
- 出典は**1行1件**の箇条書きにする。1行に2件並べない。

### 直訳調・冗長表現の言い換え

| 使わない | 使う |
|---|---|
| 〜することができます | 〜できます |
| 〜することが可能です | 〜できます |
| 〜を行う／〜を実施する | 動詞そのもの（実行する、作る） |
| これにより／それによって | 主語を立てて書く |
| 〜という点において | 〜は／〜では |
| 〜に関して | 〜は／〜では |
| 〜の場合においては | 〜のときは |

### 節ごとの字数配分

地の文だけを数えます（コード・表・図・見出し・出典は含めない）。

| 節 | 地の文の上限 | 必須の視覚要素 |
|---|---|---|
| きょうの3行 | 180（1行60字） | — |
| ① ベストプラクティス | 1,000 | 図1枚＋実行可能なコード／設定1つ以上 |
| ② 深掘り連載 | 1,200 | 図1枚＋表1つ以上 |
| ③ すぐ効くTIPS | 450（3本×150） | 各本にコードか設定を1つ |
| ④ 事例 | 600 | 数値タイルか表を1つ |
| ⑤ 速報 | 200 | 表（いつ / 何が / どう効くか） |
| ⑥ コマンド早見 | 0 | 表のみ |
| ⑦ きょうの課題 | 700 | — |
| あすの予告 | 60 | — |
| **合計** | **4,500** | **図3枚以上・表4つ以上** |

### 節の書き出しの型（全節共通）

```
### 見出し
> 要点（3行以内、各40字以内）
（図または表）
（コード・設定）
（補足の地の文。3文以内の段落で）
```

要点は Artifact では `<ul class="keypoints">`、Markdown では `>` の引用にします。

### 書き換えの見本

同じ内容を、地の文の壁から「要点＋表＋補足」に割った例です。

**❌ before**（1段落259字。版ごとの挙動が地の文に埋まっていて、拾い読みできない）

```markdown
`/verify` は自分でもレシピを書き残します。記録がない状態でビルドして動かす必要が生じると、うまくいった手順をリポジトリ直下の `.claude/skills/verify/SKILL.md`（モノレポなら触ったパッケージのディレクトリ）に書き出し、以後の実行と他のエージェントが同じ手順をたどるようにします（Claude Code v2.1.200 以降）。ルート直下に置かれた場合、この記録がバンドルの `/verify` を置き換えます。v2.1.205 以降は「実行を誤らせたとき（コマンドが失敗した、手順が抜けていた）だけ」書き換える仕様になったので、セッションごとに差分が出ることはなく、そのままコミットできます。
```

**✅ after**（結論を先に出し、版ごとの差は表に逃がす）

```markdown
> `/verify` はレシピを自分で書き残します。
> 書き出し先はリポジトリ直下の `.claude/skills/verify/SKILL.md`（モノレポなら触ったパッケージの下）。

| 版 | 書き出しの挙動 |
|---|---|
| v2.1.200 〜 | 記録がなければ、うまくいった手順を書き出す。以後は他のエージェントもそれをたどる |
| v2.1.205 〜 | 書き換えるのは「実行を誤らせたとき」だけ |

ルート直下に置かれた記録は、バンドルの `/verify` を置き換えます。
セッションごとに差分が出ないので、そのままコミットできます。
```

## 図の作法

- 図は**メカニズムを示すためのもの**。飾りの図・情報量ゼロの図は入れない。
- 構造・フロー・関係・時系列は **Mermaid** を使う。Artifact も GitHub も追加ライブラリなしで描画される。
  - Markdown 側: ```mermaid フェンス
  - Artifact HTML 側: `<pre class="mermaid">` ブロック
  - 使う種類: `flowchart` / `sequenceDiagram` / `timeline` / `mindmap` / `stateDiagram-v2`
- 「A と B の違い」「手順の対比」「設定値の一覧」は**表**にする。Mermaid で無理に描かない。
- Mermaid のノードラベルに `()` `[]` `:` を裸で入れると壊れるので、`["テキスト"]` のように必ずダブルクォートで囲う。
- **1号あたり最低3枚**。「① ベストプラクティス」と「② 深掘り連載」には必ず1枚ずつ入れる。

## コードの作法

「① ベストプラクティス」は**図とコードで示す節**です。文章だけで終わったらその日の看板は不成立です。

- **そのまま実行・貼り付けできる完全な形で書く。** 断片や省略記号（`...`）で逃げない。
- 設定ファイルは**パスを必ず添える**（`.claude/settings.json` / `.claude/skills/<name>/SKILL.md` / `CLAUDE.md` など）。JSON は抜粋ではなくそのファイルとして妥当な全体を載せる。
- コマンドは実際に打てる1行にする。プレースホルダを使うときは、直後に「`<name>` はスキル名」のように何を入れるか書く。
- **推測でキー名・オプション名・バージョンを書かない**（ガードレール2の再掲）。一次情報で確認できないものは、その論点ごと落とす。
- **アンチパターンは「なぜ失敗するのか」まで書く。** 「〜しないこと」の列挙で終わらせない。**失敗する側と正しい側を並べて対比させる**（Artifact では `<div class="vs">`、Markdown では `#### ❌ …` / `#### ✅ …` の小見出し2つ）。
- ②③⑦でもコードを出してよいが、必須なのは①。

## 品質ガードレール（違反したら書き直す）

1. **出典URLを必ず添える。** 事例・新機能・数値には出典を付ける。裏が取れない話は書かないか、「未確認」と明示する。
2. **推測でバージョン番号・機能名・料金・オプション名を書かない。** 必ず一次情報（公式ドキュメント / CHANGELOG / 公式ブログ）で確認する。確認できなければその話題を落とす。
3. **既出トピックを繰り返さない。** `state/covered-topics.md` に載っているものは扱わない。触れる必要があるときは過去号へのリンクだけにする。
4. **ネタがない日は正直に書く。** 「本日は特筆すべき新機能の発表はありませんでした」と書いてよい。埋めるために薄い話題を捏造しない。
5. **手元で試せることを優先する。** 抽象的な心構えより、今日のうちに実行できる具体を書く。
6. **読みやすさの規約に通す。** `scripts/readability-check.py` の違反を残したまま公開しない（`prompts/daily.md` の Step 2.5・2.6）。

## 原稿は2つの形で作る（混ぜない）

同じ内容を**別々に2回書きます**。片方をコピーしてもう片方にしないこと。

| 出力先 | 形式 | ルール |
|---|---|---|
| `digest/YYYY/MM/YYYY-MM-DD.md`（GitHub アーカイブ） | **純粋な Markdown** | `<div>` `<p class="src">` `<h3>` などの **HTML タグを一切入れない**。見出しは `###`、囲みは引用 `>`、出典は `出典: [タイトル](URL)`、図は ```mermaid フェンス |
| Artifact の HTML | **テンプレートのクラス構造** | `template/COMPONENTS.md` のクラスを使う。Markdown 記法（`##` や `**`）を書かない |

視覚部品の対応は次のとおりです。**どちらの形でも、情報を地の文に戻さないこと。**

| 中身 | Artifact | Markdown |
|---|---|---|
| 節の要点 | `<ul class="keypoints">` | `>` の引用の箇条書き |
| 数値の並び | `<div class="stats">` | 2列の表（値 / 何の数字か） |
| 失敗と正解の対比 | `<div class="vs">` | `#### ❌ …` / `#### ✅ …` の小見出し2つ |
| 用語の定義 | `<dl class="terms">` | 2列の表（用語 / 意味） |

GitHub 上で `<div class="item">` がそのまま文字として見えてしまうと台無しです。
**HTML タグの混入は `scripts/readability-check.py` が検査します**（Step 2.5）。

## 一次情報の見分け

- 一次情報: `docs.claude.com` / `anthropic.com/news` / `anthropic.com/engineering` / `github.com/anthropics/*`
- 二次情報（要注意）: 個人ブログ、Zenn/Qiita、Reddit、X。**事例としては価値があるが、機能の仕様の根拠にはしない。**
- 二次情報を引くときは「〜という報告があります（出典）」と伝聞であることを明示する。
